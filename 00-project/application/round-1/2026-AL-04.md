# Smart Parking Garage Management System

## My interpretation of the brief
The project is a database-centred system that models the real operation of a parking garage: floors, parking spaces, customers, vehicles, reservations, entries and exits, tariffs, subscriptions, payments, and maintenance periods. The database is not only a storage layer. It has to enforce the business rules itself: two customers must never hold overlapping reservations for the same space, the state of a space must always reflect reality, and the parking fee must be calculated correctly from the tariff and the actual parking interval.

The central technical problem is concurrency. Several users may try to reserve the same space at the same moment, so the reservation logic must run inside transactions with a locking or isolation strategy that prevents double booking without making the system unusably slow. The web interface is deliberately thin; its job is to demonstrate the database functions, not to replace them.

## Why I am a good fit for this project
I enjoy taking a physical, real-world process and turning it into a precise digital model. A parking garage is a good example: it has clear physical constraints (a space is either free or occupied, a car cannot be in two places), time-based rules (reservations, tariffs, maintenance windows), and money involved, so mistakes are visible and measurable. I find it motivating that the correctness of the system can be verified against how the real garage would behave.

I am also interested in the performance side of databases. Understanding why a query is slow by reading its execution plan, and then fixing it with the right index, is the kind of concrete, measurable engineering work I want to build my thesis on.

## Proposed approach
I plan to use Microsoft SQL Server (Developer Edition) with T-SQL, because it is free for development, has strong tooling in SQL Server Management Studio, and offers Actual Execution Plan, SET STATISTICS IO and SET STATISTICS TIME for the required performance analysis. Oracle with PL/SQL remains an option if the supervisor prefers it.

I would start with the data model: garages, floors, parking spaces, space states, customers, vehicles, reservations, parking events, tariffs, subscriptions, payments, and maintenance periods, normalised to third normal form and enforced with primary keys, foreign keys, unique constraints and check constraints. Then I would implement the core business logic as stored procedures: searching for available spaces in a time interval, creating and cancelling reservations, handling entry and exit, and calculating the parking fee. Triggers would maintain the space state and write an audit log.

For concurrency I would implement and compare at least two strategies for the reservation procedure: a pessimistic approach using explicit locking hints (UPDLOCK, HOLDLOCK) inside a transaction, and an optimistic approach based on snapshot isolation with conflict detection and retry. I would build a small load-testing script that fires concurrent reservation requests for the same space and measure conflicts, consistency, and response time under both strategies.

A reproducible test-data generator (a script that creates at least one hundred thousand reservation and parking events with realistic time distributions) would feed the performance work. I would write at least ten complex queries (interval searches, occupancy and utilisation per floor and hour, revenue reports, customer and vehicle history) and optimise at least five of them with indexes, comparing execution plans and I/O statistics before and after.

Finally, a simple web interface would let a customer search spaces, create and cancel reservations and view their history, and let an operator see current occupancy and basic statistics. The web layer would only call the stored procedures.
