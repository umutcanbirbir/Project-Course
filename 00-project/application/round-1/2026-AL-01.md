# Design and Performance Optimization of a Relational Database for an Electric Vehicle Charging Network with AI Support

## My interpretation of the brief
The project models a real electric vehicle charging network as a relational database: charging stations and their charging points, users and their vehicles, reservations, charging sessions, energy measurements, tariffs, payments and technical faults. The first half of the work is careful data modelling with database-level integrity rules. The second half is measurement-driven performance optimisation: filling the database with a large, reproducible synthetic dataset, writing realistic operational queries, reading their execution plans, and improving them with indexes and query rewrites.

The AI part is not about building a model. An external LLM service is asked for optimisation suggestions on a few queries, and the student has to check whether those suggestions are correct, executable and actually faster, using their own measurements. The result is a documented, repeatable optimisation process, not a full application.

## Why I am a good fit for this project
I like modelling physical systems in software, and a charging network is a good subject: physical devices with states (free, charging, faulty), sessions with start and end times, energy that is measured every few seconds, and tariffs that turn measurements into money. Every entity corresponds to something real, which makes it easy to judge whether the model is right.

I am also attracted by the measurable nature of the task. A query either gets faster or it does not, and the execution plan explains why. Comparing my own indexing decisions with what an AI service proposes is a realistic modern workflow, and I want to learn where such tools help and where they are wrong.

## Proposed approach
I plan to use Microsoft SQL Server (Developer Edition) with T-SQL, because it is free, well documented, and provides Actual Execution Plan, SET STATISTICS IO, SET STATISTICS TIME and Query Store for the required analysis. Oracle with PL/SQL is an alternative if the supervisor prefers it.

I would first design the model with at least ten related tables in third normal form: stations, charging points, connector types, users, vehicles, reservations, charging sessions, energy measurements, tariffs, payments and technical events. Integrity rules such as "a charging point can have only one active session" and "a session cannot end before it starts" would be enforced with constraints and, where needed, triggers.

Next I would write a reproducible data generator (a Python script with a fixed random seed) that produces at least one hundred thousand charging sessions and at least one million timestamped measurement records with realistic daily patterns. Then I would write at least ten complex queries that reflect real operational questions: station utilisation per hour, revenue per tariff, users with unusual consumption, points with repeated faults, availability in a time window, using joins, aggregation, CTEs and window functions.

For at least five queries I would record the baseline plan and statistics, then design simple, composite and filtered indexes, and re-measure. A small measurement script would run each query several times before and after optimisation and store the timings so the comparison is repeatable. A stored procedure for starting and closing a session, and a trigger for logging technical events, would cover the required business logic.

For the AI component I would send three selected queries with their schema to an LLM API, collect the suggested indexes or rewrites, review them by hand, and then measure them with the same script. I would never execute AI-generated DDL automatically. I would document what the service got right, what it got wrong, and the data-protection limits of sending schema information to an external service.
